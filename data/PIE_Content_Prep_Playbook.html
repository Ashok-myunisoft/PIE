Introduction

Understanding PIE

The Product Intelligence Engine is the single source of truth that powers both operational QuickStart delivery and every GTM asset the organisation produces — from landing pages and demo scripts to chatbots and trial onboarding journeys.

PIE as Content Engine + GTM Engine

GoodBooks targets three commercial engagement models. The 70/25/5 model defines how customers are served — and how PIE content must be prioritised:

70%
Standard

Out-of-box profile, auto-provisioned, no customisation. QuickStart eligible. PIE must be fully calibrated (L4+) for every module in the profile.

25%
Configure

Profile + deviation answers drive variant selection and additional config items. Estimation engine must be seeded with real hours for each variant path.

5%
Custom

Bespoke development required. PIE still contributes the standard modules and base estimation. Custom delta is tracked separately.

PIE is not merely a configuration database — it is the single publishing engine that feeds every downstream consumer simultaneously. Build the content once; let it flow everywhere:

Content Maturity Model

Every module has a maturity level (L0–L5). QuickStart eligibility and GTM readiness gates are tied to maturity. Use this model to prioritise content sprints and communicate progress to stakeholders.

L0

Ghost

Module exists in the database with a code and name, but no content of any kind. Cannot be referenced in a profile or used in a demo.

QuickStart: ❌ Not Eligible GTM: ❌ Not Ready
L1

Skeleton

Module has a description and at least one Config Item. No Variants defined. Enough to place in a catalogue, not enough for any workflow.

QuickStart: ❌ Not Eligible GTM: ❌ Not Ready
L2

Draft

Variants are defined but lack Implications, Estimation Rules, or Training Topics. Useful for internal workshops; not yet fit for customer-facing use.

QuickStart: ❌ Not Eligible GTM: ⚠️ Internal Only
L3

Functional

All 8 content types present (Module, ConfigItems, Variants with Implications, Training Topics, UAT Scenarios, Migration Objects, Estimation Rules, KPIs). Estimation ConfidenceScore < 70 — likely seeded from documents rather than real delivery data.

QuickStart: ⚠️ Conditional GTM: ⚠️ With Caveats
L4

Calibrated

At least 5 real implementation outcomes have been fed back. ConfidenceScore ≥ 80. PlainLanguageDesc populated for all Variants. Health Score ≥ 85. KPIs include benchmark values from real customer data.

QuickStart: ✅ Eligible GTM: ✅ Ready
L5

Intelligence

Signal detection active — new variants are being proposed by the AI gateway from support tickets, usage patterns, and implementation notes. KMS atoms live. AEO targeting active. Module drives competitive differentiation narratives.

QuickStart: ✅🚀 AEO Ready GTM: ✅🚀 Full Power
Sprint goal: Move each module from its current level to L4 (Calibrated). L5 happens organically once the signal detection pipeline is running. Prioritise modules that are L2 or L3 and appear in a QuickStart profile — they block customer activation.

Cross-Process Variant Library

These variants affect multiple process flows simultaneously. Define them once as Profile Deviation Questions — not as module-level variants — because answering one question changes config items across several modules at the same time. This is the most common source of scope surprises in ERP implementations.

Variant Axis Processes Affected Implication Summary
Approval Workflow Depth
1-level / 2-level / 3-level 		P2P O2C R2R Each additional level adds ~0.5h config time. 3-level requires role hierarchy setup. Affects PO, SO, journal, and payment approval flows simultaneously.
Multi-currency
Single / Multi 		P2P O2C R2R Adds FX revaluation config (+2h). Requires currency table setup and daily rate import. Adds 3–4 UAT scenarios across AP, AR, and GL modules.
Multi-location / Multi-branch
Single / Multi 		P2P O2C R2R I&W H2R PSD All master data (vendors, customers, inventory) multiplied per location. Adds ~30% to total estimation hours. Inter-branch transfers require additional UAT scenarios.
Tax Regime
Single / Multi 		P2P O2C R2R H2R Multi-tax adds 2–4h configuration. Requires tax consultant involvement for validation. Affects invoice, payroll, and GL posting rules across all financial modules.
Intercompany Transactions
None / Present 		P2P O2C Requires matching entity setup for both parties. Adds elimination journal configuration in R2R. High complexity flag — add RiskNote and escalate to senior consultant review.
Budget Control Mode
None / Soft / Hard 		P2P O2C Hard control requires commitment accounting setup (+3h). Blocks transactions exceeding budget — must be UAT-tested for edge cases (partial POs, blanket orders). Soft control adds warning-only logic.
Workshop facilitation tip: Capture these six cross-process variants in the first 15 minutes of any profile assembly session (Session Type C). Their answers determine the scope of config items that surface across all subsequent module sessions — getting them wrong early multiplies rework.

Content Health Score

The Health Score (0–100) is calculated automatically from the counts of each content type. Use it to objectively prioritise modules for sprint work and to determine QuickStart and GTM eligibility.

Health Score Formula
Health Score (out of 100) =
  (ConfigItems>=5 ? 10 : ConfigItems×2)          // max 10
+ (Variants>=3 ? 15 : Variants×5)                 // max 15
+ (Implications>=Variants×2 ? 15 : 0)             // max 15
+ (TrainingTopics>=3 ? 10 : TrainingTopics×3)     // max 10
+ (UATScenarios>=5 ? 15 : UATScenarios×3)         // max 15
+ (MigrationObjects>=1 ? 5 : 0)                     // max 5
+ (EstimationRules>=2 ? 10 : 0)                     // max 10
+ (EstimationConfidence>=80 ? 10 : 5)               // max 10 (min 5 if rules exist)
+ (KPIs>=2 ? 10 : KPIs×5)                         // max 10
≥ 85 QuickStart Eligible

Module has sufficient depth across all content types. Can be included in QuickStart profiles and auto-provisioned during trial activation.

70 – 84 Conditional

Module is usable but has gaps. Can be included in profiles with partner guidance. Prioritise in next sprint to reach QuickStart threshold.

< 70 Not Eligible

Insufficient content for reliable deployment. Treat as a priority sprint target. Do not include in QuickStart profiles or GTM assets until score reaches ≥85.

GTM Readiness — Additional Criteria (beyond QuickStart)

A module is GTM Ready when it passes the QuickStart threshold and meets all four of the following criteria:

  • ≥5 Profile.Keywords populated (drives AEO targeting and SEO)
  • ≥2 KPIs with benchmark values (Good / Average / Poor) — required for ROI messaging
  • ≥1 kms_knowledge_ref linked — confirms CMS content is live for this module
  • PlainLanguageDesc populated for all Variants — required for QuickStart selection screens and chatbot responses

Gap Analysis & Sprint Planning

Run 2-week sprints targeting 3–5 modules per sprint. Each sprint aims to move all assigned modules to Health Score ≥85. Sprint team composition: 1 Domain Expert + 1 Implementation Consultant + 1 Content/ECA per module set.

Prioritisation Rule: Prioritise modules by two criteria — (1) the module is included in a high-priority QuickStart profile, OR (2) the module has the most support tickets (highest ROI to fix gaps). When in doubt, pick the module that unblocks the most profiles.

Quality Gates

Three gates determine what a module can be used for. Modules must pass Gate 1 before Gate 2; Gate 2 before Gate 3. Gates are enforced by the PIE Admin publish workflow — the system will not allow promotion past a gate with unmet criteria.

Gate 1 Publish

Required to set IsActive = 1 and make the module available in the system.

  • ≥5 Config Items with ItemCategory and Description
  • ≥3 Variants with ≥1 Implication each
  • ≥3 Training Topics (≥1 per applicable TopicCategory)
  • ≥5 UAT Scenarios (at least 1 Simple, 1 Medium)
  • ≥1 Estimation Rule per EngagementType offered
  • ≥2 KPIs with Description
  • ≥1 kms_knowledge_ref populated (CMS linkage started)
Gate 2 QuickStart Eligible

Required to include this module in QuickStart profiles and auto-provisioning. Requires Gate 1 first.

  • ≥1 Profile includes this module
  • All mandatory Config Items have DefaultValue set
  • Estimation ConfidenceScore ≥ 70
  • All mandatory UAT Scenarios have Preconditions defined

Health Score ≥ 85 is required to pass this gate automatically.

Gate 3 GTM Ready

Required for use in marketing assets, landing pages, demo scripts, and AEO targeting. Requires Gate 2 first.

  • Profile.Keywords ≥ 5 terms populated
  • ≥2 KPIs have Good / Average / Poor benchmark values
  • PlainLanguageDesc populated for ALL Variants
  • ≥1 KMS atom authored and live in CMS for this module

Only GTM Ready modules appear in landing page templates and demo scripts.

Knowledge Pipeline

From PIE to EAP — The Knowledge Flow

PIE → EAP KMS Flow

Every PIE entity follows this eight-step pipeline from workshop to live chatbot and ER activation. Each step has a clear owner and a defined artefact.

1 — Workshop Content Capture

Teams capture raw knowledge using the Phase 2 capture cards. Output: handwritten / digital notes, whiteboards, screenshots. Owner: facilitator + domain experts.

2 — AI Conversion: Notes → PIE Entities

Post-session, the ECA team runs the Notes → PIE Entity JSON prompt. Output: draft JSON for ConfigItems, Variants, TrainingTopics, UATScenarios, KPIs. Owner: ECA / content team.

3 — PIE Admin Review & Publish

Domain expert reviews AI output in PIE Admin. Corrections applied. Module marked IsActive=1 when Publish Gate criteria are met. kms_knowledge_ref fields populated per entity. Owner: PIE Admin + domain expert.

4 — AI Generation: Draft KMS Atoms

ECA team runs the Batch KMS Atom Generator prompt against the published PIE module JSON. Output: array of Concept/Fact/Rule/Process atoms. Owner: ECA team.

5 — CMS Authoring & Brand Review

ECA reviews AI-drafted atoms for brand voice, accuracy, and completeness. Edits applied in CMS. Atoms published (status = Published). Owner: ECA / content editor.

6 — KMS Pipeline Ingest

Published CMS atoms flow into the EAP KMS pipeline via the ingest job. Atoms are indexed for RAG retrieval. Verify via KMS Admin: all atom kmsRefs appear in the RAG index. Owner: EAP platform team.

7 — ER Trigger Activation

ER trigger mapping is updated: each screen URL / event fires the relevant KMS atom as a WorkInstruction, Tip, Assessment, or Tour. ER uses kms_knowledge_ref from the PIE entity to fetch the atom. Owner: ER configuration team.

8 — Chatbot & AEO Activation

EAP AI Gateway serves RAG-backed Q&A using the indexed atoms. AEO surfaces relevant atoms during trial and demo sessions based on profile match. Run the Chatbot Q&A Quality Check prompt before marking a module chatbot-ready. Owner: EAP AI team + GTM team.

kms_knowledge_ref Convention

Every PIE entity that has a published KMS atom must have its kms_knowledge_ref field populated with the atom's canonical reference. This reference is how ER and the chatbot locate the correct content at runtime.

PIE Entity Atom Type kmsRef Pattern Example
Module Concept kms-concept-{domain}-{module} kms-concept-ap-accounts-payable
Config Item Fact kms-fact-{domain}-{config-item} kms-fact-ap-invoice-matching-type
Variant Rule kms-rule-{domain}-{variant} kms-rule-ap-matching-type-3way
Training Topic Process kms-process-{domain}-{topic} kms-process-ap-vendor-master-setup
UAT Scenario Process kms-process-qc-{scenario} kms-process-qc-ap-3way-match
KPI Concept kms-concept-kpi-{kpi-code} kms-concept-kpi-ap-days-outstanding

Naming Rules

  • Domain = module functional area in kebab-case (e.g., accounts-payable, inventory, payroll)
  • Record slug = descriptive name in kebab-case — no module prefix (domain already scopes it)
  • Type must be one of: concept, fact, process, rule
  • Separator: always hyphen — never underscore or slash
  • Case: always lowercase — never camelCase or PascalCase

Common Mistakes

  • kms-fact-accounts_payable-invoice_matching — underscores not allowed
  • kms-Fact-AP-InvoiceMatching — no mixed case
  • kms-fact-ap-ap-invoice-matching — don't repeat domain in slug
  • kms-data-ap-invoice-matching — "data" is not a valid type

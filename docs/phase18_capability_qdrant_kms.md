# v0.18 — Capability Model + Qdrant KMS

## Goal

v0.18 consumes the knowledge already generated by v0.17. It does **not** call
OpenAI again for unchanged knowledge.

The authoritative Knowledge Management Store is **Qdrant**.

```text
v0.17 generated knowledge
        |
        v
Capability / Feature normalization
        |
        v
Local embedding (no paid API)
        |
        v
Qdrant: pie_knowledge
        |
        v
Future Usage / RAG / Agents
```

The v0.17 JSON files remain generation/audit artifacts. They are not the KMS.

## Hierarchy

```text
Product
  -> Module
      -> Functionality
          -> Capability
              -> Feature
                  -> Screen
```

v0.18 never silently claims that Functionality and Capability are the same.
If no explicit capability exists, the existing Functionality is retained only
as a `derived_from_functionality_candidate` capability and is marked for review.
Human/source-confirmed mappings can be placed in `capability_map.json`.

## Existing v0.17 knowledge

The default source is:

`outputs/phase17-ai-knowledge/knowledge/`

This is preferable to `knowledge_manifest_v17.json` because a v0.17 run may
have been generated with `--limit`, while the per-screen directory can contain
the complete previously generated knowledge.

## Qdrant

Start locally:

```powershell
docker compose -f docker-compose.qdrant.yml up -d
```

Initialize:

```powershell
python -m pie_agent.cli kms-init
```

Build the capability model without an LLM:

```powershell
python -m pie_agent.cli capability-model
```

Publish all existing v0.17 knowledge into Qdrant:

```powershell
python -m pie_agent.cli kms-publish
```

Publish only records cleared for production retrieval:

```powershell
python -m pie_agent.cli kms-publish --published-only
```

Search production-approved knowledge:

```powershell
python -m pie_agent.cli kms-search --query "leave application approval workflow"
```

Search including review-required knowledge:

```powershell
python -m pie_agent.cli kms-search --query "leave application approval workflow" --include-review
```

Check collection:

```powershell
python -m pie_agent.cli kms-stats
```

## Qdrant payload

Each point stores the vector plus structured knowledge:

- knowledge_id
- product
- module
- functionality
- capability
- capability_basis
- feature
- screen_id
- knowledge_type
- title
- content
- evidence_ids
- source_types
- confidence
- review_required
- publication_status
- generation_method
- claim_type
- source_hash
- knowledge_version
- generated_at

Therefore Qdrant is not merely an embedding cache. It is the KMS.

## API

After starting PIE:

- `GET /kms/health`
- `GET /kms/stats`
- `GET /kms/knowledge/{knowledge_id}`
- `GET /kms/search?q=leave%20application`

By default `/kms/search` excludes `REVIEW_REQUIRED` records. Set
`include_review=true` only when reviewing the generated knowledge.

## Idempotency

Point IDs are deterministic from:

`knowledge_id + knowledge_version`

Running `kms-publish` again for the same v0.17 knowledge therefore upserts
the same Qdrant points rather than creating duplicate points.

## Cost control

Do not run:

`generate-ai-knowledge`

again for unchanged screens.

v0.18 embeds the existing knowledge locally using a deterministic hashing
vectorizer. This adds no OpenAI token/API cost.

A later release can replace the local vectorizer with a local
SentenceTransformers model without changing the Qdrant KMS contract.


## Production Qdrant Server

PIE v0.18 is configured to use the existing Qdrant server at `http://217.217.249.121:6333`.
The authoritative PIE KMS collection is `pie_knowledge`. Do not run the bundled local Qdrant compose file for this production setup.

Set in `.env`:

```env
QDRANT_URL=http://217.217.249.121:6333
QDRANT_COLLECTION=pie_knowledge
QDRANT_API_KEY=
```

Use `kms-init` to create the collection if it does not exist, then `kms-publish` to load the existing v0.17 knowledge. No OpenAI call is made by these commands.
